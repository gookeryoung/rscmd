# rscmd 小模型调用指南与硬件配置需求

> 状态基线：2026-11-16，rscmd `0.1.0`，11 个工具、8 个内建命令。
> 工具数以当前工作区实际构建并运行的 `rscmd tools --json` 为准；其中 `csv` 来自
> 尚未提交的并行改动，提交基线 HEAD 上为 10 个工具（无 `csv`）。若该改动不落地，
> 删去本文中 `csv` 相关条目即可，其余结论不变。
> 本文所有命令与输出均在本仓库当前版本上实际运行过；标注「实测」的数字来自本机，
> 标注「估算」的数字是量级参考，不是 benchmark 结论。测量方法和复现命令见第 8 节。

## 0. 结论先行

1. **rscmd 本身几乎不占用资源。** 单次 CLI 调用热态约 6 ms、峰值内存约 10 MB 量级；
   MCP 常驻进程约 7 MB，单次工具调用往返约 0.04 ms（均实测，见 5.1）。
   真正的成本在模型推理，不在工具执行。
2. **小模型接入优先用「MCP 取 schema + 调用同一套工具」或「全 CLI + `--json`」两条路。**
   前者让客户端自动发现 `inputSchema`，后者最简单、最容易审计。
3. **对小模型最重要的三条纪律：**
   - 每次调用都带 `--json`；
   - 只信退出码和错误信封里的 `code` / `field` / `expected` / `hint`，不要解析自然语言；
   - `filesearch` 和 `csv` 必须显式 `--limit`，否则默认不限制。
4. **硬件上 7B/8B 就能驱动 rscmd，14B 是性价比甜点，32B 用于复杂多步任务。**
   32B Q4 想交互流畅，建议 24–32 GB 显存 + 64 GB 内存；纯 CPU 跑 32B 只适合离线批处理。

# 第一部分 如何用小模型调用 rscmd

## 1. 调用面

### 1.1 入口总览

| 入口 | 形态 | 适合谁 | 稳定性 |
|---|---|---|---|
| `rscmd run <工具> ... --json` | 一次进程、一个结果 | 小模型/脚本直接调用 | 高，推荐 |
| `rscmd <工具> ... --json` | 直达形式（兼容别名） | 手工调试 | 高，但不推荐写进提示词 |
| `rscmd schema --json` | 全局自描述 `rscmd-schema/1` | 启动时加载全局参数与工具清单 | 高 |
| `rscmd tools --json` | 工具清单 `rscmd-tools/1` | 只需要工具目录 | 高 |
| `rscmd mcp` | JSON-RPC over stdio | 支持 MCP 的模型客户端 | 高，但语义与 CLI 略有差异 |
| Python `rscmd.invoke` / `run_argv` | 进程内原生调用 | Python 宿主 | 高；**不支持 `mcp`** |

说明：

- `rscmd` 不带任何参数时打印帮助并以 `0` 退出，不是错误。
- `run` 是推荐入口；`rscmd case ...` 这类直达形式仍然可用，两者走同一套解析与执行。
- 工具别名（如 `jsonfmt`、`casetool`）在 CLI 和 MCP `tools/call` 里都可用；
  但 `tools/list` 只列出规范名，建议模型始终用规范名。

```console
$ rscmd version --json
{"data":{"name":"rscmd","version":"0.1.0"},"ok":true,"schema":"rscmd-result/1","tool":"version"}
```

### 1.2 结果信封 `rscmd-result/1`

成功结果写到 **stdout**，一行紧凑 JSON（不是 pretty JSON）：

```json
{
  "schema": "rscmd-result/1",
  "ok": true,
  "tool": "case",
  "data": { "text": "hello_world" }
}
```

实际单行输出（字段按字典序排列，不要依赖字段顺序）：

```console
$ rscmd run case --mode snake HelloWorld --json
{"data":{"text":"hello_world"},"ok":true,"schema":"rscmd-result/1","tool":"case"}
```

字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| `schema` | string | 固定 `rscmd-result/1` |
| `ok` | bool | 成功为 `true`；`doctor` 结论不通过时可为 `false`（退出码 5） |
| `tool` | string | 工具规范名；解析阶段的用法错误时可能为空串 |
| `subcommand` | string | **可选**，仅当工具有真实下级子命令时出现，例如 `path normalize` |
| `data` | object | 工具结果；不同工具字段不同 |

`subcommand` 的真实例子：

```console
$ rscmd path normalize a/../b --json
{"data":{"input":"a/../b","op":"normalize","path":"b"},"ok":true,"schema":"rscmd-result/1","subcommand":"normalize","tool":"path"}
```

要点：

- 加 `--json` 后 stdout 只有这一行信封，适合直接 `json.loads`。
- 不加 `--json` 时，人读输出因工具而异（有的只输出 `text`，有的输出 pretty JSON），
  **不适合程序解析**。
- 信封是紧凑单行；`--verbose` 只往 stderr 写跟踪行，不污染 stdout。

### 1.3 错误信封 `rscmd-error/1` 与退出码

错误写到 **stderr**，stdout 为空。这是小模型/宿主最容易踩的坑之一：
只读 stdout 的封装会看到「空输出 + 非零退出码」。

```console
$ rscmd run case --mode nope HelloWorld --json
{"code":"INVALID_MODE","exit_code":3,"expected":"snake/camel/pascal/kebab","field":"mode","kind":"invalid_input","message":"未知命名风格: nope","ok":false,"schema":"rscmd-error/1","tool":"case"}
# 退出码 3
```

字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| `schema` | string | 固定 `rscmd-error/1` |
| `ok` | bool | 固定 `false` |
| `tool` | string | 工具名；解析阶段错误可能为空串 |
| `kind` | string | 错误大类，见下表 |
| `code` | string | 具体错误码，如 `INVALID_MODE`、`IO` |
| `message` | string | 可读说明 |
| `field` | string? | 出错参数名（可选） |
| `expected` | string? | 期望值/取值范围（可选） |
| `hint` | string? | 自纠建议（可选） |
| `exit_code` | number | 与进程退出码一致 |

`kind` 与退出码一一对应：

| kind | 退出码 | 典型 code | 含义 |
|---|---|---|---|
| `runtime` | 1 | `IO`、`TIMEOUT`、`NET_*` | 运行期失败（文件不存在、网络、超时） |
| `usage` | 2 | `USAGE`、`MISSING_TOOL` | 命令形状/必需参数错误 |
| `invalid_input` | 3 | `INVALID_ARGS`、`INVALID_MODE`、`INVALID_JSON`、`INVALID_REGEX`、`INVALID_ENCODING` | 参数值不合法 |
| `not_found` | 4 | `TOOL_NOT_FOUND` | 目标工具不存在 |
| `check_failed` | 5 | —（`doctor` 结论） | 检查类命令结论不通过 |
| `interrupted` | 130 | `INTERRUPTED` | 用户 Ctrl+C |

另外两个常见边界：

- 未知子命令或未知工具走 clap 解析，返回 `USAGE`/2，**不是** `TOOL_NOT_FOUND`/4：

  ```console
  $ rscmd run nope --json
  {"code":"USAGE","exit_code":2,"kind":"usage","message":"error: unrecognized subcommand 'nope'\n\nUsage: rscmd run [OPTIONS] [COMMAND]\n\nFor more information, try '--help'.","ok":false,"schema":"rscmd-error/1","tool":""}
  ```

- `rscmd info nope --json` 才是 `TOOL_NOT_FOUND`/4：

  ```console
  $ rscmd info nope --json
  {"code":"TOOL_NOT_FOUND","exit_code":4,"hint":"使用 `rscmd tools` 查看可用工具","kind":"not_found","message":"未知工具: nope","ok":false,"schema":"rscmd-error/1","tool":"info"}
  ```

### 1.4 `rscmd schema`：`rscmd-schema/1`

```console
$ rscmd schema --json
{"data":{"builtins":["run","tools","info","schema","version","doctor","completion","mcp"],"global":{...},"schema":"rscmd-schema/1","tools":[...],"version":"0.1.0"},"ok":true,"schema":"rscmd-result/1","tool":"schema"}
```

（上面是节选，`...` 为截断标记，真实输出是一行完整 JSON。）

`data` 含：

- `schema`：固定 `rscmd-schema/1`
- `version`：rscmd 版本
- `tools`：工具元数据列表（与 `tools --json` 同源）
- `builtins`：内建命令名
- `global`：全局参数的 JSON Schema（`--json`、`--limit`、`--timeout` 等）

**重要限制：`schema` / `info` / `tools` 里的工具条目只有元数据，没有各工具的
`inputSchema`。** 需要参数级 schema 时，用：

- `rscmd mcp` 的 `tools/list`（返回完整 `inputSchema`），或
- 仓库 `schema/<tool>.json` 生成物。

实测体积（单行字符数）：`tools --json` 约 2.5k，`schema --json` 约 3.4k，
MCP `tools/list` 约 5.2k。后者包含参数 schema，信息量最大。

### 1.5 `rscmd tools`：`rscmd-tools/1`

```console
$ rscmd tools --json
{"data":{"schema":"rscmd-tools/1","tools":[{"aliases":["casetool"],"examples":["rscmd case --mode snake HelloWorld"],"gui":false,"name":"case","python":"structured","side_effects":"none","summary":"命名风格转换（snake/camel/pascal/kebab）"}, ...],"version":"0.1.0"},"ok":true,"schema":"rscmd-result/1","tool":"tools"}
```

（节选，`...` 为截断标记。）

- 每个条目含 `name`、`aliases`、`summary`、`side_effects`、`gui`、`python`、`examples`。
- `side_effects` 取值：`none` / `read` / `write` / `network` / `destructive`。
  当前 11 个工具只有 `none` 与 `read`。
- `--for-llm` 会过滤掉 GUI 工具；当前没有 GUI 工具，所以输出与不加时相同。

### 1.6 `rscmd mcp`：JSON-RPC over stdio

启动方式：

```console
$ rscmd mcp
```

常见 MCP 客户端配置形如（`command` 需在 PATH，或改成二进制绝对路径）：

```json
{
  "mcpServers": {
    "rscmd": { "command": "rscmd", "args": ["mcp"] }
  }
}
```

- 从 stdin 逐行读 JSON-RPC 请求，向 stdout 逐行写响应。
- 支持方法：`initialize`、`ping`、`tools/list`、`tools/call`。
- 通知（无 `id`）不返回响应；空行忽略；stdin 关闭后正常退出。
- 协议版本常量 `2025-06-18`；`initialize` 会回显客户端请求的 `protocolVersion`，
  缺省时用服务端常量。
- 服务端是**单线程串行**处理，没有并发；需要并行时起多个进程。
- MCP 模式**不接受全局参数**（`--json`、`--limit` 等）；参数全部放在 `arguments` 里。
- 当前暴露范围：有 JSON 入口且非 GUI 的工具，即全部 11 个。

真实会话（一次进程内连续三条请求）：

```console
$ printf '%s\n' \
  '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18"}}' \
  '{"jsonrpc":"2.0","id":2,"method":"ping"}' \
  '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"case","arguments":{"mode":"snake","text":"HelloWorld"}}}' \
  | rscmd mcp
{"id":1,"jsonrpc":"2.0","result":{"capabilities":{"tools":{}},"protocolVersion":"2025-06-18","serverInfo":{"name":"rscmd","version":"0.1.0"}}}
{"id":2,"jsonrpc":"2.0","result":{}}
{"id":3,"jsonrpc":"2.0","result":{"content":[{"text":"hello_world","type":"text"}],"isError":false}}
```

（示例用 bash 的 `printf`。PowerShell 等价写法：把三行 JSON 放进 `@('...','...')`
再管道给 `rscmd mcp`，或直接由客户端写 stdin。）

`tools/list` 的条目形如（单个条目节选）：

```json
{
  "name": "case",
  "description": "命名风格转换（snake/camel/pascal/kebab）",
  "inputSchema": {
    "type": "object",
    "properties": {
      "mode": { "type": "string", "default": "snake" },
      "text": { "type": "string" }
    },
    "required": ["text"]
  }
}
```

工具执行失败时，**不是 JSON-RPC error**，而是 `result.isError=true`，错误信息在
`content[0].text` 里（通常是 `错误[CODE]` 前缀的人读格式；未知工具等直接给纯文本）：

```console
$ printf '%s\n' \
  '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"case","arguments":{"mode":"nope","text":"x"}}}' \
  '{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"nope","arguments":{}}}' \
  | rscmd mcp
{"id":3,"jsonrpc":"2.0","result":{"content":[{"text":"错误[INVALID_MODE]: 未知命名风格: nope\n  字段: mode\n  期望: snake/camel/pascal/kebab","type":"text"}],"isError":true}}
{"id":4,"jsonrpc":"2.0","result":{"content":[{"text":"未知工具: nope","type":"text"}],"isError":true}}
```

协议级错误用 JSON-RPC `error`：

| 场景 | code |
|---|---|
| 无法解析 JSON | `-32700` |
| 请求不是对象 | `-32600` |
| 未知方法 | `-32601` |
| `tools/call` 缺 `params` 或工具名 | `-32602` |

MCP 与 CLI 的语义差异，务必写进提示词：

- MCP 没有 `rscmd-result/1` 信封；成功结果是 `content[0].text`。
  若结果有 `text` 或 `json` 字符串字段就返回该字符串；否则返回 `data` 的紧凑 JSON。
- MCP 没有退出码；失败靠 `isError` 判断，可从文本里的 `错误[CODE]` 提取具体错误码
  （未知工具等纯文本错误没有该前缀）。
- `filesearch` / `csv` 在 MCP 里直接传 `limit` 参数（命令行里对应全局 `--limit`）。
- `path` 在 CLI 里是 `path normalize ...` 子命令，在 MCP 里是
  `{"op":"normalize","path":"..."}`。

## 2. 小模型最容易踩的坑

| # | 坑 | 现象 | 正确做法 |
|---|---|---|---|
| 1 | `--limit` 是全局参数 | 以为 `--limit` 只属于 `filesearch`，或忘了传导致输出巨大 | `filesearch`/`csv` 显式 `--limit 20`；0 表示不限制 |
| 2 | 不加 `--json` | 人读输出随工具变化，无法稳定解析 | 所有程序化调用都带 `--json` |
| 3 | 只读 stdout | 错误时 stdout 为空，误判为「没结果」 | 同时捕获 stderr；先看退出码，再看 `code` |
| 4 | 用自然语言判断错误 | 把 `message` 当唯一依据，跨语言/版本易碎 | 用 `kind` + `code` + `field` + `expected` |
| 5 | 把未知工具当 `not_found` | `rscmd run nope` 实际是 `USAGE`/2 | 需要区分时用 `info` 或先查 `tools` |
| 6 | 路径分隔符混用 | `filesearch` 返回 `a/b.txt`，Windows 其他工具可能习惯 `\` | `rscmd` 的 `path`/`filesearch` 统一输出 `/`；输入两者都接受 |
| 7 | 编码差异 | Windows 控制台非 UTF-8 时人读中文乱码 | 用 `--json` 且按 UTF-8 解码；终端可 `chcp 65001` |
| 8 | 把 `schema` 当参数 schema | `rscmd schema --json` 只有元数据，没有 `inputSchema` | 参数 schema 用 MCP `tools/list` 或 `schema/*.json` |
| 9 | 假设 schema 能表达互斥 | `hash` 的 `text` / `file` 在 schema 里都可选，运行时才校验 | 提示词里写清「二选一」，并准备读 `INVALID_ARGS` |
| 10 | 位置参数当选项 | `filesearch --root .`、`wc --text hi` 会报 unexpected argument | 看 `Usage:` 行：`filesearch <ROOT>`、`which <PROGRAM>`、`wc <TEXT>` |
| 11 | 在 MCP 里等 JSON 信封 | `content[0].text` 是文本或紧凑 JSON | 按 MCP 语义解析，不要复用 CLI 信封解析器 |
| 12 | 以为 `--workers` 能加速 | 当前 11 个工具没有消费 `--workers` 的分支 | 不要用它做并发；并发靠多进程/客户端调度 |
| 13 | JSON 参数名 ≠ CLI 选项 | `--percentiles`、`--no_header` 会报错 | `stat --percentile`、`csv --no-header`、`regex --size-limit`；`path` 用子命令 |

补充：`--confirm`、`--dry-run`、`--timeout` 是框架预留的全局参数，当前 11 个工具
都没有副作用或网络分支，实际调用可以完全不传。它们不是「小模型必填项」。

## 3. 推荐工具子集与优先级

### 3.1 分级

| 级别 | 工具 | 为什么 | 主要风险 |
|---|---|---|---|
| A：先掌握 | `case`、`wc`、`json_fmt`、`codec`、`hash`、`stat`、`path`、`which` | 输入输出小、确定性强、几乎无副作用 | `hash` 的 text/file 二选一；`path` 子命令形状 |
| B：按需开放 | `csv`、`regex` | 真正常用的数据处理 | 输出可能很大；正则语法是 Rust regex，不是 PCRE |
| C：慎用/必须限流 | `filesearch` | 能扫整棵树，信息量大 | 不传 `--limit` 会返回大量结果；内容检索只匹配文本文件 |
| 不建议先给 | 无（当前没有 GUI/破坏性工具） | — | — |

给小模型的最小可用集合建议是 A 级 8 个；只有任务明确需要「找文件」时才加
`filesearch`，需要「解析表格/正则」时再加 `csv`/`regex`。

### 3.2 系统提示模板

下面这段可以直接放进系统提示，再附上裁剪后的工具清单：

```text
你是命令行助手。所有操作都通过 rscmd 完成，不要凭空发明命令或参数。

调用规则：
1. 每次调用都必须带 --json；只从 stdout 读取 rscmd-result/1 信封。
2. 退出码 0 表示成功；2=命令/参数用法错误；3=参数值非法；4=工具不存在；
   1=运行失败；5=检查未通过；130=用户中断。
3. 退出码非 0 时，读 stderr 的 rscmd-error/1，优先看 code、field、expected、hint。
   同一错误最多重试 2 次；重复出现就停止并说明原因。
4. 不要猜测参数。参数名和类型以工具清单 / inputSchema 为准。
5. filesearch 和 csv 必须带 --limit，默认用 20。
6. 不要解析人读输出；不要依赖 JSON 字段顺序。
7. 找不到文件或路径不存在时，先确认路径，不要反复重试同一个路径。

说明：工具清单里的参数名是 MCP/JSON 参数名；CLI 调用时，text、json、values、
pattern、program、root、input 大多是位置参数，不要写成 --text。
例外：hash --file、csv --text、regex --file 是显式选项；path 用子命令。

可用工具：
- case: 命名风格转换。参数：text（必填）、mode（snake/camel/pascal/kebab，默认 snake）。
- wc: 统计行/词/字符/字节。参数：text（必填）。
- json_fmt: 校验并格式化 JSON。参数：json（必填）、minify（可选）。
- codec: base64/hex/url 编解码。参数：text（必填）、mode（默认 base64）、decode（可选）。
- hash: 计算 SHA-256。参数：text 或 file 二选一。
- stat: 数值统计。参数：values（必填，可多个）、percentiles（可选，如 25,90）。
- path: 路径处理。CLI 形状：path normalize/join/relative/is-abs ...
- which: 查找可执行文件。参数：program（必填）；找不到时返回 path=null 且退出码 0。
- filesearch: 文件检索。参数：ROOT（位置参数）、--name、--content、--limit。
- csv: CSV/JSON 互转。参数：INPUT 或 --text 二选一、--to json|csv、--limit。
- regex: 正则匹配/替换。参数：PATTERN（位置参数）、TEXT 或 --file 二选一、--replace。
```

### 3.3 工具清单怎么裁剪

- 全量 `tools/list` 实测约 5.2k 字符（约 1.2–1.5k tokens）。对 7B + 4k 上下文偏紧，
  对 14B 以上通常可接受。
- 7B/8B 建议只给 A 级 8 个工具的一行描述 + 必填参数，总长控制在 1.5k 字符以内。
- 不要给「所有参数的所有说明」；只保留必填项、枚举值、以及会改变行为的默认值。
- 不要同时保留 CLI 别名和规范名；只保留规范名，减少混淆。
- MCP 客户端可以自行按名称过滤 `tools/list` 的结果再喂给模型；服务端不提供过滤参数。

### 3.4 few-shot 示例怎么选

建议 3 条即可，覆盖「成功、参数错误、无结果/失败」：

1. **成功且输出短**：`case` 或 `stat`，展示「调用 → 读 `data` → 用一句话回答」。
2. **参数错误后自纠**：`case --mode nope` 收到 `field=mode`、`expected=...`，
   改成合法值重试一次。
3. **无结果/运行失败**：`which` 返回 `path=null`（退出码 0，不是错误），
   或 `hash --file 不存在` 返回 `IO`（退出码 1）；展示「停止并说明」，而不是死循环。

不要选：长输出 `filesearch` 全量结果、需要多轮工具链的复杂任务、依赖当前目录的示例。
few-shot 里的命令要用规范名，不要用别名。

### 3.5 多轮里如何用退出码决定重试还是放弃

| 退出码 | 模型动作 | 重试上限 |
|---|---|---|
| 0 | 读取 `data`，继续任务或回答 | — |
| 2 `usage` | 命令形状错/缺必填参数；按 `Usage:` 修正一次 | 1 次 |
| 3 `invalid_input` | 读 `field`/`expected`/`hint`，改参数值 | 2 次 |
| 4 `not_found` | 不要重试；从工具清单里换一个，或询问用户 | 0 次 |
| 1 `runtime` | 路径/权限/IO 问题；换路径或让用户确认 | 1 次（必须改变输入） |
| 5 `check_failed` | 这是「检查不通过」的结论，不是故障；如实报告 | 0 次 |
| 130 `interrupted` | 停止，等待用户 | 0 次 |

一条实用规则：**同一 `code` + 同一 `field` 连续出现两次，就停止重试**，
把 `message`、`field`、`expected` 原样汇报给用户。

### 3.6 用 `--limit` 和字段裁剪控制上下文

- `--limit` 是全局参数，当前只被 `filesearch` 和 `csv` 消费；`0` 或不传表示不限制。
- 典型安全值：列表类 20，内容检索 5–10，CSV 预览 20。
- `filesearch` 的文件名模式返回 `{path, bytes}`；内容模式返回 `{path, line, text}`，
  后者更容易膨胀，建议 5–10 条。
- 不要把整个 `rscmd-result/1` 原样塞回上下文；只保留 `data` 里下一步要用的字段。
- 需要机器裁剪时，宿主侧解析 JSON 后只回传 `data.results`、`data.matched`、
  `data.truncated` 等少量字段，比让模型自己「忽略多余内容」可靠。
- 输出被截断时结果里有 `truncated: true`（`filesearch`/`csv`），模型应知道
  「还有更多结果」，必要时提高 limit 或缩小检索条件，而不是假装已看全。

## 4. 端到端调用范例

以下命令与输出均来自本仓库实际运行。为便于阅读，输出保留了原始单行 JSON。

### 范例 1：成功（单步，短输出）

用户意图：「把 `HelloWorld` 转成 snake_case。」

模型动作：

```console
$ rscmd run case --mode snake HelloWorld --json
{"data":{"text":"hello_world"},"ok":true,"schema":"rscmd-result/1","tool":"case"}
```

模型应如何回应：

> 转换结果是 `hello_world`。

要点：退出码 0；直接读 `data.text`；不需要重试。

### 范例 2：成功（多步，先找文件再算哈希）

用户意图：「找 `crates` 下的 `.toml` 文件，并告诉我 `rscmd-cli/Cargo.toml` 的 SHA-256。」

第一步：

```console
$ rscmd run filesearch crates --name "*.toml" --limit 2 --json
{"data":{"matched":2,"results":[{"bytes":352,"path":"rscmd-cli/Cargo.toml"},{"bytes":336,"path":"rscmd-core/Cargo.toml"}],"root":"crates","scanned":57,"truncated":true},"ok":true,"schema":"rscmd-result/1","tool":"filesearch"}
```

第二步（用第一步返回的相对路径，补上 root）：

```console
$ rscmd run hash --file crates/rscmd-cli/Cargo.toml --json
{"data":{"algorithm":"sha256","bytes":352,"hex":"1cdb08ec04013b4ff12b4b3a67f42d9802682c0cd1f00692391abe2a89cd22af","source":{"kind":"file","path":"crates/rscmd-cli/Cargo.toml"}},"ok":true,"schema":"rscmd-result/1","tool":"hash"}
```

模型应如何回应：

> 找到 2 个 `.toml`（结果已截断）。`crates/rscmd-cli/Cargo.toml` 的 SHA-256 是
> `1cdb08ec04013b4ff12b4b3a67f42d9802682c0cd1f00692391abe2a89cd22af`。

要点：`truncated: true` 表示还有更多；模型应说明「已截断」，不要声称「只有 2 个」。
`filesearch` 返回的是相对 `root` 的 `/` 路径，后续工具要拼回 `root`（这里为 `crates/`）。

### 范例 3：参数值错误（退出码 3，可自纠）

用户意图：「把 `HelloWorld` 转成某种命名风格。」

模型第一次调用（故意给了非法 mode）：

```console
$ rscmd run case --mode nope HelloWorld --json
{"code":"INVALID_MODE","exit_code":3,"expected":"snake/camel/pascal/kebab","field":"mode","kind":"invalid_input","message":"未知命名风格: nope","ok":false,"schema":"rscmd-error/1","tool":"case"}
# 退出码 3
```

模型读取：`code=INVALID_MODE`、`field=mode`、`expected=snake/camel/pascal/kebab`。
修正后重试：

```console
$ rscmd run case --mode snake HelloWorld --json
{"data":{"text":"hello_world"},"ok":true,"schema":"rscmd-result/1","tool":"case"}
```

模型应如何回应：

> 已按合法取值 `snake` 重试，结果是 `hello_world`。

要点：这是「参数值错」，不是「命令不存在」；`expected` 直接给出了可选值。
同一 `field` 不要连续试超过 2 次。

### 范例 4：用法错误（退出码 2，先修命令形状）

用户意图：「格式化一段 JSON，但模型忘了传必填参数。」

```console
$ rscmd run json_fmt --json
{"code":"USAGE","exit_code":2,"kind":"usage","message":"error: the following required arguments were not provided:\n  <JSON>\n\nUsage: rscmd run json_fmt --json <JSON>\n\nFor more information, try '--help'.","ok":false,"schema":"rscmd-error/1","tool":""}
# 退出码 2
```

模型应如何回应：

> 缺少必填参数 `<JSON>`。已改为传入 JSON 文本：

```console
$ rscmd run json_fmt '{"b":2,"a":1}' --json
{"data":{"json":"{\n  \"a\": 1,\n  \"b\": 2\n}"},"ok":true,"schema":"rscmd-result/1","tool":"json_fmt"}
```

> 格式化结果：
> ```json
> { "a": 1, "b": 2 }
> ```

要点：`tool` 为空、`USAGE`/2，说明错误发生在解析阶段；`Usage:` 行就是修正依据。
JSON 作为位置参数时要正确加引号，避免 shell 拆分。

### 范例 5：执行失败（退出码 1，不要盲目重试）

用户意图：「算一下 `no-such-file.txt` 的 SHA-256。」

```console
$ rscmd run hash --file no-such-file.txt --json
{"code":"IO","exit_code":1,"field":"file","kind":"runtime","message":"读取文件失败: 系统找不到指定的文件。 (os error 2)","ok":false,"schema":"rscmd-error/1","tool":"hash"}
# 退出码 1
```

模型应如何回应：

> 无法读取 `no-such-file.txt`（`IO`，字段 `file`）：文件不存在。
> 请确认路径，或告诉我正确的文件名；我不会重复用同一路径重试。

要点：`runtime`/1 表示「命令本身没问题，但执行环境失败」。先确认路径/权限，
不要原样重试；也不要把 `IO` 当成参数值错误去改 `--file` 以外的参数。

# 第二部分 硬件配置需求

## 5. rscmd 自身的资源开销（实测）

### 5.1 实测数字

测量环境：Windows 11 家庭版 10.0.26300，PowerShell 7.6.5，
Intel Core Ultra 9 285K（24 核/24 线程），63.4 GB 内存，NVIDIA RTX 5090 D 32 GB；
rscmd release 构建，二进制 3,615,232 字节（约 3.4 MiB）。

| 场景 | 实测值 | 方法 |
|---|---|---|
| `run case ... --json` 单次耗时 | 平均 **6.4 ms**（20 次） | 热态、同进程外启动、含进程创建 |
| `version --json` 单次耗时 | 平均 **6.1 ms**（20 次） | 同上 |
| `schema --json` 单次耗时 | 平均 **6.3 ms**（20 次） | 同上 |
| `filesearch . --content rscmd` | **260 ms**，扫描约 1.19 万文件 | 同一仓库、含磁盘遍历 |
| 上述 `filesearch` 峰值工作集 | **9.8 MB** | 5 ms 轮询采样 |
| MCP 常驻进程工作集 | **6.9 MB** | 200 次 `tools/call` 后 |
| MCP 单次 `tools/call` 往返 | 平均 **0.04 ms**（200 次） | 同一 stdio 会话，`case` 工具 |

解释：

- 6 ms 里大部分是进程创建/加载，不是工具逻辑；所以「多调几次 rscmd」不会成为瓶颈。
- 按 6 ms 的实测值推算，1 万次 CLI 调用的进程开销约 60 秒；同样 1 万次若走常驻
  MCP，工具执行本身可忽略，但 MCP 是串行的，且模型推理仍占绝对大头。
- `filesearch` 的 260 ms 是遍历约 1.19 万个文件的结果；目录越大越慢，但仍是
  「百毫秒级」，远小于一次模型生成。
- 以上均为热态（文件系统缓存已预热）；冷启动/杀毒扫描会更高。未测冷启动。
- 短调用（约 6 ms）太快，5 ms 轮询难以稳定采到峰值；表中的 9.8 MB 是较长调用
  `filesearch` 的采样值，短调用可参考同一二进制与常驻 MCP 的 6.9 MB，量级一致。
- MCP 的 0.04 ms 是「宿主写一行 + 读一行」的往返，含管道调度，只用于说明数量级，
  不应当作精确 benchmark。

结论：**并发调用 rscmd 几乎不吃资源。** 单进程约 7–10 MB，几十个并发也只是
几百 MB 量级；真正的内存和算力都在模型推理侧。

### 5.2 为什么瓶颈是模型推理

一次「模型驱动命令行」的循环大致是：

```text
系统提示 + 工具 schema（1–4k tokens）
        ↓ 模型 prefill
生成工具调用 JSON（50–200 tokens）
        ↓ 执行 rscmd（约 6 ms / 0.04 ms）
把结果放回上下文（几十到几百 tokens）
        ↓ 模型继续生成
```

rscmd 侧固定成本是毫秒级；模型侧成本由 **prefill（与上下文长度成正比）** 和
**decode（与输出 token 数、显存带宽成正比）** 决定。上下文越长、工具越多、
多轮越多，模型侧越慢。

因此硬件选型看的是「模型能不能放进显存/内存」以及「带宽够不够」，
而不是 rscmd 的 CPU 占用。

## 6. 量化、显存与内存的估算口径

> 以下均为**估算**，用于选型，不是实测 benchmark。实际值受模型结构、KV cache、
> batch、上下文长度、推理框架影响。

### 6.1 权重体积

近似公式：

```text
权重体积(GB) ≈ 参数量(B) × 每权重比特数 / 8
```

常见 GGUF 量化的每权重比特数（含部分元数据开销）：

| 量化 | 每权重约 | 7B 权重 | 14B 权重 | 32B 权重 |
|---|---|---|---|---|
| Q4_K_M | ~4.5 bit | ~4.4 GB | ~9.0 GB | ~19.9 GB |
| Q5_K_M | ~5.5 bit | ~5.3 GB | ~10.5 GB | ~23.5 GB |
| Q8_0 | ~8.5 bit | ~8.1 GB | ~15.5 GB | ~34.5 GB |

（表中体积为估算，不同模型/工具链会有 ±10% 差异。）

### 6.2 运行时还要加什么

- **KV cache**：随上下文线性增长。4k 上下文粗略量级：
  7B 约 0.5–1 GB，14B 约 1–2 GB，32B 约 2–4 GB（FP16 KV，GQA 会小一些）。
- **框架/计算缓冲**：1–2 GB。
- **CPU 推理**：权重 + KV + 2–4 GB 进程开销，再给操作系统和其他应用留 4–8 GB。
- **GPU 推理**：权重 + KV + 1–2 GB 开销必须能放进显存；放不下就会部分卸载到 CPU，
  速度会明显下降。

### 6.3 选型速查

| 模型档位 | 量化 | 纯 CPU 内存（最低/建议） | GPU 显存（最低/建议） | 磁盘占用（建议） |
|---|---|---|---|---|
| 7B/8B | Q4_K_M | 16 GB / 32 GB | 8 GB / 12 GB | 10–15 GB |
| 14B | Q4_K_M | 32 GB / 48–64 GB | 12 GB / 16 GB | 20–25 GB |
| 32B | Q4_K_M | 32–48 GB / 64 GB | 24 GB / 32 GB | 40–60 GB |
| 32B | Q5_K_M | 48–64 GB / 96 GB | 32 GB / 48 GB | 50–70 GB |

说明：

- 32B Q4 在 24 GB 卡上属于「能跑但上下文和并发要克制」；32 GB 更稳。
- 纯 CPU 的 32B 建议 64 GB 内存；如果同时开浏览器/IDE，96 GB 更从容。
- 磁盘建议 NVMe SSD：模型加载时间主要看顺序读；机械盘会让冷加载非常慢。
- 同一模型保留多个量化会成倍占磁盘；只留一个主用量化即可。

**显卡档位举例（估算）：**

| 显存 | 典型卡 | 能流畅跑的档位 | 说明 |
|---|---|---|---|
| 8 GB | RTX 4060 / 4060 Ti 8G | 7B Q4 | 14B 需要部分卸载，速度明显下降 |
| 12 GB | RTX 4070 / 5070 | 7B Q4/Q5，14B Q4（紧） | 14B 建议降上下文或换 16 GB 卡 |
| 16 GB | RTX 4060 Ti 16G / 4070 Ti Super | 14B Q4/Q5 | 32B Q4 只能部分卸载 |
| 24 GB | RTX 3090 / 4090 | 32B Q4（上下文克制） | 4k 上下文、低并发更稳 |
| 32 GB | RTX 5090 | 32B Q4/Q5 | 32B 交互式 agent 的舒适档 |

CPU 侧需要 AVX2（2013 年后的主流桌面 CPU 基本都有），AVX-512 更好；
生成速度更吃内存带宽，而不是单纯的核心数。Apple Silicon 的统一内存是另一条路线，
本文未展开。

**CPU 档位举例（估算）：** 7B 用 Ryzen 5 7600 / Core i5-13400 级别即可；
14B 建议 Ryzen 7 7700 / Core i7-13700 级别；32B 建议 Ryzen 9 7950X /
Core i9-14900K / Ultra 9 级别，并配 64 GB 以上内存。

## 7. 三档配置与吞吐量级

> 下表吞吐为**估算**，假设：单请求、batch=1、上下文 2k tokens、
> 输出 100 tokens、GQA 模型、无多卡张量并行；**不含模型首次加载**。
> CPU 档假设 8–24 个现代大核（AVX2/AVX-512）、DDR5；GPU 档为消费级单卡。

### 7.1 7B/8B：能驱动命令行

| 路径 | 最低配置 | 建议配置 | 量化 | 生成速度（估算） | 单轮响应（估算） |
|---|---|---|---|---|---|
| 纯 CPU | 8 核 / 16 GB / 10 GB 磁盘 | 12–16 核 / 32 GB / NVMe | Q4_K_M | 6–15 tok/s | 20–40 s |
| GPU | 8 GB 显存 / 16 GB 内存 | 12 GB 显存 / 32 GB 内存 | Q4_K_M | 40–90 tok/s | 2–4 s |

适合：单步工具调用、格式转换、简单检索、分类/抽取。7B 在「按 schema 填参数」
上已经可用，但复杂多步容易跑偏。

### 7.2 14B：性价比甜点

| 路径 | 最低配置 | 建议配置 | 量化 | 生成速度（估算） | 单轮响应（估算） |
|---|---|---|---|---|---|
| 纯 CPU | 12–16 核 / 32 GB / 20 GB 磁盘 | 16–24 核 / 64 GB / NVMe | Q4_K_M | 3–8 tok/s | 35–60 s |
| GPU | 12 GB 显存 / 32 GB 内存 | 16 GB 显存 / 32–64 GB 内存 | Q4_K_M | 25–60 tok/s | 3–5 s |

适合：需要理解稍长提示、在多工具间选择、按错误信息自纠的任务。
14B + 16 GB 显存是「本地 agent 工具调用」比较均衡的一档。

### 7.3 32B：复杂多步任务

| 路径 | 最低配置 | 建议配置 | 量化 | 生成速度（估算） | 单轮响应（估算） |
|---|---|---|---|---|---|
| 纯 CPU | 16–24 核 / 48–64 GB / 40 GB 磁盘 | 24 核 / 96 GB / NVMe | Q4_K_M | 1.5–4 tok/s | 90–150 s |
| GPU | 24 GB 显存 / 64 GB 内存 | 32 GB 显存 / 64 GB 内存 | Q4_K_M | 18–40 tok/s | 5–8 s |

适合：多步规划、跨文件检索后综合、需要较强指令遵循与纠错的任务。
纯 CPU 的 32B 单轮就要 1.5–2.5 分钟，只适合离线/批处理，不适合交互式 agent。

### 7.4 两端对照

| 维度 | 「只是想让模型驱动命令行」 | 「32B 做复杂多步任务」 |
|---|---|---|
| 模型 | 7B/8B Q4_K_M | 32B Q4_K_M（或 Q5_K_M） |
| CPU | 8–12 核即可 | 16–24 核 |
| 内存 | 16–32 GB | 64 GB（建议 96 GB 更从容） |
| 显存 | 可不配；或 8–12 GB | 24 GB 最低，32 GB 建议 |
| 磁盘 | 10–15 GB NVMe | 40–60 GB NVMe |
| 生成速度 | CPU 6–15 tok/s；GPU 40–90 tok/s | CPU 1.5–4 tok/s；GPU 18–40 tok/s |
| 单轮响应 | CPU 20–40 s；GPU 2–4 s | CPU 90–150 s；GPU 5–8 s |
| 5 轮任务 | CPU 2–3 分钟；GPU 10–20 秒 | CPU 7–12 分钟；GPU 25–40 秒 |
| 体验定位 | 轻量自动化、单步工具 | 交互式多步 agent |

「5 轮任务」是按每轮约 2k 输入 + 100 输出粗乘，未计工具执行时间（可忽略）和网络。

### 7.5 并发与吞吐

- **rscmd 侧**：CLI 每次约 6 ms、约 10 MB；并行几十个进程没有压力。
  MCP 服务是单线程串行，吞吐高但延迟不叠加；需要并行就起多个 MCP 进程。
- **模型侧**：batch 能提高总吞吐，但会增加单请求延迟；agent 循环通常 batch=1。
  32B 在 24 GB 卡上并发 2–4 路时，KV cache 会明显挤占显存，需要降上下文或排队。
- 真正的并发上限由显存（KV cache）和模型框架决定，不由 rscmd 决定。

## 8. 复现命令

测量耗时（PowerShell 7，热态，20 次取平均）：

```powershell
$exe = (Resolve-Path .\target\release\rscmd.exe).Path
$n = 20
$ms = (Measure-Command {
  1..$n | ForEach-Object { & $exe run case --mode snake HelloWorld --json | Out-Null }
}).TotalMilliseconds
"case avg_ms={0:N1}" -f ($ms / $n)
```

测量 `filesearch` 耗时与峰值内存：

```powershell
$exe = (Resolve-Path .\target\release\rscmd.exe).Path
$sw = [System.Diagnostics.Stopwatch]::StartNew()
& $exe filesearch . --content rscmd --limit 20 --json | Out-Null
$sw.Stop()
"filesearch_wall_ms={0:N0}" -f $sw.Elapsed.TotalMilliseconds
```

测量 MCP 常驻内存与往返（同一会话 200 次）：

```powershell
$exe = (Resolve-Path .\target\release\rscmd.exe).Path
$psi = New-Object System.Diagnostics.ProcessStartInfo
$psi.FileName = $exe; $psi.Arguments = 'mcp'
$psi.RedirectStandardInput = $true; $psi.RedirectStandardOutput = $true
$psi.UseShellExecute = $false
$p = [System.Diagnostics.Process]::new(); $p.StartInfo = $psi; $null = $p.Start()
$p.StandardInput.WriteLine('{"jsonrpc":"2.0","id":0,"method":"initialize","params":{}}')
$null = $p.StandardOutput.ReadLine()
$sw = [System.Diagnostics.Stopwatch]::StartNew()
1..200 | ForEach-Object {
  $p.StandardInput.WriteLine('{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"case","arguments":{"mode":"snake","text":"HelloWorld"}}}')
  $null = $p.StandardOutput.ReadLine()
}
$sw.Stop(); $p.Refresh()
"mcp_avg_ms={0:N2}" -f ($sw.Elapsed.TotalMilliseconds / 200)
"mcp_ws_mb={0:N1}" -f ($p.WorkingSet64 / 1MB)
```
